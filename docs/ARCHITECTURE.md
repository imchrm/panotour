## ADR-001: Собственный редактор вместо форка Marzipano Tool

**Решение:** Пишем собственный редактор хотспотов с нуля. Marzipano Tool не форкается
и не используется как основа.

**Обоснование:**
- Исходный код Marzipano Tool **закрыт** и не будет открыт. Разработчики явно закрыли
  issue #133 как `wontfix`, сославшись на технический долг.
- Статические файлы Tool доступны как минифицированный JS — это реверс-инжиниринг,
  не разработка. Поддерживать такой форк невозможно.
- Написать собственный редактор, ограниченный задачей расстановки хотспотов, —
  принципиально меньший объём работы, чем поддержка чужого legacy-кода.
- **Главное преимущество:** полный контроль над схемой `tour.json`. Любая новая фича
  (targetYaw, InfoPanel, аудиогид, карта) — это добавление поля в JSON и обработчика
  во viewer. Никаких ограничений чужого API.

**Компромисс:** Тайлинг панорам (нарезка equirectangular → CubeGeometry) не входит в
браузерную часть редактора. Используется отдельный Node.js CLI (`tiler`).

**WebAssembly тайлер — не планируется.** Теоретически реализуем через libvips-wasm +
Worker, но требует cross-origin isolation (`Cross-Origin-Opener-Policy: same-origin` +
`Cross-Origin-Embedder-Policy: require-corp` на каждый HTML-документ и все ресурсы).
Это ломает YouTube iframe в InfoPanel (не cross-origin isolated). Node.js tiler
покрывает все реальные сценарии без этих ограничений.

## ADR-002: Monorepo (npm workspaces)

**Решение:** Три пакета в одном репозитории: `editor`, `viewer`, `tiler`.
Управление через npm workspaces (встроено в npm 7+, без Lerna/Turborepo).

**Обоснование:**
- `editor` и `viewer` разделены концептуально (разные runtime: React SPA vs
  статический HTML), но тесно связаны через схему `tour.json`.
- Общие типы (`TourData`, `Scene`, `Hotspot`) могут быть вынесены в
  `packages/shared/types.ts` и использованы в обоих пакетах без дублирования.
- npm workspaces достаточно для трёх пакетов. Lerna/Turborepo — избыточно.

**Структура:**
```
panotour/
  package.json          { "workspaces": ["packages/*"] }
  packages/
    editor/             React + Vite + TypeScript
    viewer/             Vanilla JS (статика, копируется в output экспорта)
    tiler/              Node.js CLI
```

## ADR-003: Viewer — Vanilla JS, не React

**Решение:** `packages/viewer/` — чистый Vanilla JS без фреймворка.

**Обоснование:**
- Viewer — статический HTML/CSS/JS, который разворачивается на хостинге
  без сборочного шага. Пользователь скачивает ZIP и кладёт на сервер.
- React в viewer означал бы: либо бандл в ZIP (лишние ~150 KB), либо
  необходимость сборки на стороне пользователя перед деплоем.
- Marzipano — не React-библиотека. Интеграция через DOM API естественна.
- Вся сложная UI-логика (редактирование, формы) — в редакторе. Viewer отображает
  готовые данные, его логика проста: загрузить JSON, создать сцены, навесить обработчики.

## ADR-004: Центральный контракт — `tour.json`

**Решение:** Единственная точка связи между редактором и viewer — файл `tour.json`.
Редактор генерирует, viewer читает. Схема версионируется полем `version`.

**Обоснование:**
- Полная независимость частей системы: редактор и viewer можно разрабатывать
  и тестировать раздельно.
- Расширение функционала = добавление поля в JSON. Обратная совместимость
  обеспечивается через `version` и проверку наличия поля перед использованием.
- JSON читается человеком — удобно для отладки и ручного редактирования.

**Правило расширения схемы:**
Новые поля всегда опциональны на стороне viewer (`hotspot.targetFov ?? DEFAULT_FOV`).
Это гарантирует, что старые туры работают с новым viewer без перегенерации.

## ADR-005: Позиционирование хотспотов — клик по Marzipano canvas

**Решение:** В редакторе панорама рендерится через Marzipano. Клик по canvas
конвертируется в yaw/pitch через API Marzipano.

**Обоснование:**
- Marzipano — единственный способ корректно отобразить equirectangular/cubemap
  панораму с правильной проекцией. Canvas-рисование вручную неприемлемо.
- Использование одной и той же библиотеки в редакторе и viewer гарантирует, что
  хотспот, поставленный в редакторе, окажется ровно там же во viewer.

**Подтверждено:** `view.screenToCoordinates(coords, options?)` присутствует
в публичном API Marzipano v0.10.2 — реализован в `RectilinearView` и `FlatView`.
Метод используется в `PanoramaCanvas.tsx` без каких-либо обходных путей.

## ADR-006: Экспорт — ZIP + File System Access API

**Решение:** Два режима экспорта:
1. **ZIP** (все браузеры): JSZip + FileSaver.js → скачать архив.
2. **Папка** (Chrome/Edge): File System Access API `showDirectoryPicker()` →
   записать файлы напрямую в выбранную директорию.

**Обоснование:**
- ZIP — универсально, работает везде, не требует разрешений.
- Экспорт в папку удобнее при итеративной разработке: не нужно каждый раз
  распаковывать архив. Но File System Access API поддерживается только
  Chromium-браузерами.
- Graceful fallback: кнопка экспорта автоматически определяет поддержку API
  и показывает соответствующий вариант. Firefox всегда получает ZIP.

## ADR-007: Отказ от модификации marzipano.js

**Решение:** Библиотека `marzipano.js` не форкается и не модифицируется.
Используется исключительно публичный API.

**Обоснование:**
- Форк создаёт постоянный технический долг при обновлениях библиотеки.
- Публичный API (`Viewer`, `Scene`, `RectilinearView`, `hotspotContainer`)
  достаточен для всех трёх фаз viewer и для нужд редактора.
- Низкоуровневый `Layer/Stage` API задокументирован и публичен — если
  высокоуровневого API не хватит, используем его без форка.

## ADR-009: Редактор — одна текстура без тайлинга (EquirectGeometry)

**Решение:** `PanoramaCanvas` загружает полное equirectangular-изображение через
`Marzipano.EquirectGeometry` как единую текстуру, без нарезки на тайлы.

**Обоснование:**
- Редактор — инструмент разработчика на десктопе. Файл уже в RAM браузера
  (выбран через `input[type=file]`), сеть не нужна.
- Тайлинг в браузере требует Node.js или WASM (см. ADR-001). Генерировать тайлы
  внутри редактора ради превью избыточно — для этого есть отдельный `tiler`.
- `EquirectGeometry` с одним уровнем `{ width: 4000 }` — простейшая интеграция,
  достаточная для позиционирования хотспотов.

**Ограничение:** При панорамах 8192px+ текстура может занимать до 128 MB VRAM.
На GPU без поддержки текстур > 4096px (старые/мобильные) возможны артефакты.
Это известное ограничение редактора, не viewer.

**Возможное улучшение (backlog):** Downscale до 2048–4096px перед загрузкой через
`<canvas>` + `toBlob()`. Детализации в редакторе этого достаточно.

## ADR-008: Переходы — оркестрация через setTimeout, не через Promise-цепочку

**Решение:** `TransitionEngine` управляет последовательностью Zoom → Fade → Land
через явные `setTimeout` с константами из `TRANSITION`.

**Обоснование:**
- `scene.lookTo()` не возвращает Promise (void). Completion callback отсутствует
  в публичном API. Единственный вариант синхронизации — таймауты с известными
  `transitionDuration`.
- `scene.switchTo()` также void. Нет события "переход завершён".
- Таймауты с именованными константами (`TRANSITION.ZOOM_DURATION`) читаемы и
  предсказуемы. Альтернатива (polling `view.yaw()`) — хрупко и избыточно.

**Последовательность (текущая реализация — «вдох + рывок + приземление»):**
```
t=0    : lookTo(hotspot, WIDE_FOV=100°, 80ms)              // вдох: FOV расширяется
t=80   : lookTo(hotspot, ZOOM_IN_FOV=20°, 520ms)           // рывок: FOV сужается резко
t=444  : switchTo(FADE_DURATION=280ms)                     // fade на 70% рывка
t=724  : animateFov(20°→targetFov, 650ms, easeOutCubic)    // приземление (RAF, без lookTo)
t=1374 : переход завершён (_busy = false)
```

Фаза приземления намеренно использует `requestAnimationFrame` вместо `lookTo` —
это единственный момент без конкурирующей анимации lookTo, поэтому RAF-управление
FOV с кастомной кривой easeOutCubic не создаёт конфликтов с Marzipano.
